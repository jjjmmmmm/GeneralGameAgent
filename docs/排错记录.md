## P1 [已解决] serve.py 启动卡死（config 打印后无响应，端口不开）

- **现象**：`_start_serve_d5.ps1` 启动 serve.py 后，日志停在 config 摘要打印处，进程存活但 CPU=0、内存不再增长，`Test-NetConnection 127.0.0.1 -Port 5555` 一直 False，等待 >130 秒无进展。
- **期望**：约 36~40 秒后日志出现 `Server running on port 5555`，端口可连接。
- **日志**：`results/serve_d5.log` 末尾为 config 摘要（模型架构、参数量），其后无 `Server running`；`serve_d5.log.err` 为空。
- **相关文件**：`_start_serve_d5.ps1`（启动脚本）、`NitroGen/nitrogen/shared.py`（load_model）、`~/.cache/huggingface/hub/models--google--siglip2-large-patch16-256/`（视觉编码器缓存）。
- **已尝试**：
  1. 杀进程重启多次 → 同样卡住；
  2. 检查 HF 缓存目录 → siglip2 缓存**完整**（model.safetensors 3.5GB + config + tokenizer）；
  3. 检查 GPU → 占用仅 1.4GB（模型未进 GPU），确认卡在 load_model 阶段；
  4. **根因**：transformers 加载已缓存模型时仍会发 HEAD 请求到 HF 检查更新，无代理时该请求阻塞（默认重试 + 超时），导致加载卡死；
  5. **解决**：启动脚本设 `$env:HF_HUB_OFFLINE="1"` 强制离线使用本地缓存 → ~40 秒正常就绪。
- **结论**：离线模式是 serve 启动的必选项（无代理环境）；已内置到 `_start_serve_d5.ps1`，并写入演示说明与 README。

## P2 [已解决] 残留 serve 进程导致端口冲突，新 serve 静默卡死

- **现象**：自走演示说明时发现端口 5555 被一个**系统 python**（`D:\Python312\python.exe`）启动的 serve.py 占用；随后用 venv 启动的新 serve 绑定失败但进程仍存活，看起来"卡住"。
- **期望**：同一端口只有一个 serve 在监听；新启动的 serve 应正常绑定 5555。
- **日志**：新 serve 日志停在 config 摘要（与 P1 现象类似但根因不同）；旧 serve 日志在 `C:\Users\Lenovo` 侧（非项目内）。
- **相关文件**：`NitroGen/scripts/serve.py`（bind tcp://*:5555，无端口占用保护）。
- **已尝试**：
  1. `Get-NetTCPConnection -LocalPort 5555` 找出监听 PID → 是系统 python 而非 venv；
  2. `Get-CimInstance Win32_Process -Filter "Name='python.exe'"` 列出全部 python 进程 → 发现两个 serve（系统 python + venv 各一）；
  3. **解决**：按命令行过滤 `*serve.py*` 批量 `Stop-Process -Id` 清理全部 serve，再从干净状态启动。
- **结论**：启动 serve 前必须先确认端口空闲；排障用 `Win32_Process.CommandLine` 而非仅按进程名（进程名相同无法区分）。

## P3 [已解决] PowerShell 读取 UTF-8 文档中文乱码

- **现象**：`Get-Content results/test_set_metrics.md` 显示中文全为乱码（如"娴嬭瘯闆嗚瘎娴嬫寚鏍?）。
- **期望**：正常显示中文。
- **日志**：无（显示层问题）。
- **相关文件**：所有 UTF-8 编码的 .md 文档（results/*.md、docs/*.md）。
- **已尝试**：`Get-Content -Encoding UTF8` → 正常；`chcp 65001` → 当前会话正常。
- **结论**：Windows PowerShell 5.1 默认按系统 ANSI（GBK）读文件；读 UTF-8 文件必须 `-Encoding UTF8`。已写入演示说明（步骤 4/5 命令）。
